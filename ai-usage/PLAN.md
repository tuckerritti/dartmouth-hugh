# Plan: Dartmouth Dining Email Subscription Portal

## Context

Satisfies the DALI Lab API Challenge (rubric requires 2-3 APIs/platforms, comprehensive README, deployment encouraged) by combining three:

1. **Dartmouth Dining API** — `https://menu.dartmouth.edu/menuapi/mealitems?dates=YYYYMMDD` _(the "new" technology for the Learning Journey)_
2. **Google OAuth** — users sign in to identify themselves
3. **Gmail (SMTP via App Password)** — emails sent from your @dartmouth account; subscribed users are BCC'd

Owner sets up an App Password once (requires 2-Step Verification on the Google account). Other users sign in with Google, choose breakfast/lunch/dinner, and toggle a master "subscribed" switch. A scheduler runs at 07:00, 11:00, 17:00 ET, fetches the day's menu for FoCo / Collis / Hop, and sends one email per meal with all opted-in users in BCC.

## Architecture

- **Frontend**: Next.js 15 (App Router) + TypeScript, **statically exported** (`output: 'export'` in `next.config.ts`). The build emits plain HTML/CSS/JS; no Node server runs the frontend. All data fetching happens client-side.
- **Backend**: **Bun** + TypeScript + Express, single instance. Bun runs `.ts` files directly — no separate compile step in dev. File layout mirrors the `xrds-signout-backend` style: `app.ts` bootstrap, `config.ts`, `database.ts`, `routes.ts`, `controllers/*.controller.ts`, `middleware/*.ts`.
- **Database**: Postgres (one instance on the VPS, alongside the backend), accessed through **Prisma ORM**. Schema lives in `prisma/schema.prisma`; migrations are generated and applied with the Prisma CLI (`bun prisma migrate dev` / `bun prisma migrate deploy`).
- **Comms**: REST API over HTTPS. **No cookies, no server-side session state.** Frontend holds the Google ID token in React memory and sends it as `Authorization: Bearer <idToken>` on every request; backend verifies on each call. When the token expires, the user re-signs in. This is the in-memory-only auth model.

## Data model (Prisma → Postgres)

```prisma
// prisma/schema.prisma
generator client { provider = "prisma-client-js" }
datasource db    { provider = "postgresql"; url = env("DATABASE_URL") }

model User {
  email       String       @id
  name        String?
  createdAt   DateTime     @default(now()) @map("created_at")
  preferences Preferences?

  @@map("users")
}

model Preferences {
  email      String   @id
  subscribed Boolean  @default(false)
  breakfast  Boolean  @default(false)
  lunch      Boolean  @default(false)
  dinner     Boolean  @default(false)
  updatedAt  DateTime @updatedAt @map("updated_at")
  user       User     @relation(fields: [email], references: [email], onDelete: Cascade)

  @@map("preferences")
}
```

Migrations are generated and applied with `bun prisma migrate dev` (development) and `bun prisma migrate deploy` (production). `database.ts` instantiates a single `PrismaClient` and exposes typed data-access functions (`upsertUser`, `getPreferences`, `updatePreferences`, `getSubscribersFor`) — controllers never import the client directly.

## Auth flow (in-memory only)

1. Frontend uses Google Identity Services to sign in → receives a JWT ID token.
2. Frontend stores the token in React state only (no localStorage, no cookie).
3. Every API call sends `Authorization: Bearer <idToken>`.
4. Backend middleware verifies the token via `google-auth-library`'s `verifyIdToken({ audience: GOOGLE_CLIENT_ID })` on each request, attaches `req.user = { email, name }`, and upserts the user row on first sight.
5. Token expires (~1 hour) or page reload → user re-signs in. Google's auto-select makes this nearly silent for return visitors.

## REST API (high level)

- `GET  /api/me` — returns email + preferences, or 401
- `GET  /api/preferences`
- `PUT  /api/preferences` — `{ subscribed, breakfast, lunch, dinner }`

(No `/auth/*` endpoints needed — auth happens implicitly via the bearer token on every call.)

## Backend layout

- **`app.ts`** — bootstrap: helmet, cors, body parser, mounts `routes(app)`, registers `errorHandler`, starts cron, calls `app.listen`.
- **`config.ts`** — single default-exported object built from `process.env` (Bun loads `.env` automatically).
- **`database.ts`** — instantiates `PrismaClient`; named-exports data-access functions used by controllers and services.
- **`routes.ts`** — `export default function routes(app: Express)` — registers every endpoint with its middleware chain.
- **`controllers/me.controller.ts`**, **`preferences.controller.ts`** — request handlers in the `(req, res, next)` style with `try { … } catch (err) { return next(err); }`.
- **`middleware/requireAuth.ts`** — verifies the Google ID token and attaches `req.user`.
- **`middleware/errorHandler.ts`** — terminal error middleware; logs and returns `ERR_500_INTERNAL_ERROR`.
- **`services/dining.ts`** — fetch today's menu, filter by mealPeriod (Breakfast/Lunch/Dinner) and venue (FoCo, Collis, Hop), group by venue → category for rendering.
- **`services/mailer.ts`** — `nodemailer` over Gmail SMTP with the App Password. HTML email grouped by venue. Sends to `GMAIL_USER` with all subscribers in BCC.
- **`services/scheduler.ts`** — `node-cron` with `timezone: "America/New_York"`, jobs at 07:00 / 11:00 / 17:00. Each: query opted-in recipients → fetch+filter menu → send (skip if either is empty).

## Configuration

**Backend env**: `DATABASE_URL`, `GOOGLE_CLIENT_ID`, `GMAIL_USER`, `GMAIL_APP_PASSWORD`, `FRONTEND_ORIGIN`, `PORT`.
**Frontend env**: `NEXT_PUBLIC_GOOGLE_CLIENT_ID`, `NEXT_PUBLIC_API_URL`.
Validate with zod at boot; fail fast.

## Deployment (VPS)

- One VPS hosting backend + Postgres.
- `systemd` units for the Node backend (auto-restart) and Postgres (already provided by the distro).
- `nginx` reverse proxy in front of the Node process, terminating TLS via Let's Encrypt (`certbot`).
- Frontend served by `nginx` directly from `frontend/out/` (the static export). No Node process for the frontend.
- Add the VPS domain to Google OAuth's authorized JavaScript origins.
